# 断点阈值与断点 token 刻意不共享、不跨包引用

`EnvUtil.BREAK_POINT`（utils，`{ MD: 768, XL: 1200 }`）是设备分类（`isDesktop` / `isTablet` / `isMobile` 等）的默认宽度参数来源；`BREAK_POINT_TOKEN`（hooks / `useResponsive`）是响应式布局档位的默认阈值表。二者都描述「宽度断点」，但我们**刻意**让它们各自保持独立字面量、互不引用、不抽公共常量。

**状态**：已接受（accepted）

## 背景

设备分类按「物理设备 + 英寸带」语义工作（如 1366×768 笔记本按英寸带被判为平板，由 `envUtil.test.ts:172` 钉死）；响应式布局按「纯宽度档位」语义工作。两套语义有意并存，且设备分类只用到最小档位（MD / XL），无需引入响应式那套完整档位。

## 决策

- utils 的 `EnvUtil.BREAK_POINT` 维持独立字面量，仅覆盖设备分类所需的最小档位。
- hooks 的 `BREAK_POINT_TOKEN` 维持独立字面量，供 `useResponsive` 使用。
- 二者不跨包引用、不提炼公共断点模块。

## 原因（权衡）

- **难逆转**：该分工散落在 utils 与 hooks 两包，并被测试钉死，改动成本高。
- **反直觉**：未来读者极易想把两套断点「统一」成一个常量——本 ADR 阻止这种无背景的「修复」。
- **真实取舍**：共享可消除重复，但会强制两包耦合、把响应式档位语义拽进设备分类（或反之），反而模糊各自语义边界。我们选重复以换取语义独立。
